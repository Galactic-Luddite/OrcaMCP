test of the texture displacement tools showed an agent cannot judge texture work from `render_plate_view` -- nothing

## What the code actually does (corrections to the brief)

1. **One pass, one shader, fixed lights.** `OrcaMCPPlateUtils::RenderThumbnail` (OrcaMCPPlateUtils.cpp:393-561) draws
   every model part on the plate with the `thumbnail` shader (`resources/shaders/{110,140}/thumbnail.{vs,fs}`): two
   lights fixed in eye space (`LIGHT_TOP_DIR`, `LIGHT_FRONT_DIR`), specular on, no clipping plane, no uniform for the
   light. `gouraud` has `use_static_light` / `static_light_dir` (the realistic view, GLCanvas3D.cpp:9628) but always
   adds the front light. `GLModel::init_from(its)` gives per-triangle normals unless the phong-smooth setting is on, so
   per-vertex lighting is flat per facet.
2. **A custom camera is a direction only, and never an eye point.** Presets and `fit: {object_index}` set
   `options.zoom_box`; an explicit `{camera_position, target}` does not, and the fit box is then every drawn volume plus
   20 % (OrcaMCPPlateUtils.cpp ~457-467), so the image is zoomed to the whole plate's contents whatever the position.
   And `frame_camera` ends in `Camera::apply_projection(box)`, whose `calc_tight_frustrum_zs_around` (Camera.cpp:520-547)
   moves the camera back along its axis until the near plane is 100 mm (`FrustrumMinNearZ`) in front of the depth box --
   which is the plate's whole build volume merged with every drawn volume. So no camera position is ever honoured; the
   zoom (pixels per mm on the target plane) makes up the framing. Close-ups of a small region therefore need a smaller
   fit box, not a nearer camera; an exact perspective needs a projection built by hand (`Camera::apply_projection(left,
   right, bottom, top, near, far)`, Camera.hpp:147).
3. **Colour paint is drawn already, the other channels are not.** `GLVolume::simple_render` (3DScene.cpp:705-800) draws a
   part with `mmu_segmentation_facets` as one model per filament in `extruder_colors` (the render passes
   `plater()->get_extruders_colors()`), even with the object palette on: the palette colour only reaches unpainted
   parts. State 0 of a painted part is its own filament's colour, not the palette, while the report and the label still
   give the palette colour (`RenderedVolume::color`). Support, seam, fuzzy skin and the eight texture masks are never
   drawn. The paint gizmos colour enforcers `TriangleSelectorGUI::enforcers_color` (0.5, 1, 0.5) and blockers
   `blockers_color` (1, 0.5, 0.5) (GLGizmoPainterBase.cpp:1262-1263; support, seam and fuzzy skin all use them); the texture
   panel tints only its active layer, (0.16, 0.79, 0.35, 0.38) (GLGizmoTextureDisplacement.cpp:1971).
4. **The panel has two texture previews.** *Fast*: the `texture_displacement_shaded` shader (gizmo .cpp:1583-1724), the
   active layer only, a parallax approximation on the base mesh, fed by panel state (`m_shaded_preview_glmodel`, the
   `m_shaded_*` members built by `rebuild_shaded_preview_mesh`, the layer's GL textures). *True*: `queue_preview_job`
   (.cpp:2394-2525) captures every painted part and runs `TextureDisplacementPreviewJob`, i.e. `build_texture_displacement`
   -- the bake's own function -- with one difference, `options.v2_max_triangles_k = 0` (no simplification), drawn with
   `gouraud_light` in colour runs (`GLGizmoTextureDisplacement::group_preview_by_color`, public static). MCP already has
   the same computation headless: `capture_texture_bake` / `plan_texture_bake` (Jobs/TextureDisplacementBakeJob.hpp:94-98,
   T0 of the texture plan) are the preview job's loop exactly. So the true preview needs no GL to compute and no upstream
   change; the fast one cannot be reproduced honestly outside the panel and is not attempted.
5. **The section view** is upstream a1ad2b4425 (#15879): `GLCanvas3D::SectionView {ratio, normal}` (GLCanvas3D.hpp:710),
   public getters `is_section_view_active`, `get_section_view_ratio`, `get_section_view_normal`; the plane is
   `_get_section_view_plane` (GLCanvas3D.cpp:12014-12036): it sweeps the volumes' bounding sphere from the camera side
   (ratio 0) to the far side (1), and the volumes keep the side `_get_volumes_clipping_plane` gives (the inverted normal).
   The cut faces are `MeshClipper::render_cut`, which reads the *plater's* camera (MeshUtils.cpp:131), so it cannot draw
   into our framebuffer; the thumbnail shader has no clipping plane either.
6. **The render runs in one main-thread call** (OrcaMCPServer.cpp ~1460: `run_on_main_thread` around
   `OrcaMCPPlateUtils::RenderPlateView`). Mesh work (a preview, distances) there would freeze the GUI and could not be
   bounded by `tool_wait_cap()`.
7. **`fit` takes `object_index`** where every other tool says `object_id`, and **view items are not strict**: no
   `additionalProperties: false`, so a misspelled or invented key (`fov`, `zoom`, `distance`) is silently ignored -- part
   of why the live test's close-up attempts looked like they worked.
8. **No GL context in any test** (nothing in `tests/` creates one). Pure render arithmetic is tested
   (`test_render_math.cpp`, `test_layer_plan.cpp`, `test_first_layer_plan.cpp`); every draw path is live-checked only.
9. **Resolution** is clamped to 32..2048 (`RenderPlateView`). With a fitted box, a 10 mm region at 2048 px is 5 um per
   pixel, so close-ups (V1) make the cap moot; it stays (decision 4).

## Rules for every task

- Every decision in a pure function, unit-tested in `tests/slic3rutils` without the app and without GL (tests/AGENTS.md:
  plain present-tense names, PascalCase tag, `WithinAbs` for floats, no `&&` in an assertion). App code on the main
  thread inside `run_on_main_thread`; mesh work on the HTTP thread from captured copies (V0's compute step).
- **The default picture does not change.** A call without the new arguments draws what it draws today (same camera
  arithmetic, same colours, same lighting). New keys only add; each task's live check renders the V9 fixture both ways.
- All option parsing and refusals happen before anything is drawn (`read_render_request`, V0), as `parse_layer_view`
  does now. A refusal is a thrown `std::runtime_error` with what to send instead (the tool's existing error path).
- `render_plate_view` stays read-only: no undo step, no panel closed, no plate invalidated, no scene change. A state
  it cannot show honestly (an open texture panel's unflushed strokes, a section with nothing cut) is said in the answer.
- Images only through `OrcaMCPImageFiles` (`new_mcp_image_path`, the system temp directory); V7 reads only paths
  `is_mcp_image_path` accepts.
- Anything a response returns in a request's shape is accepted back (CLAUDE.md "Tool list"): each strict object gets the
  "What a tool returns, sent back" test in `test_mcp_tool_arguments.cpp`.
- `next_steps` only through builders in `OrcaMCPNextSteps.cpp`, each with its case in `test_mcp_next_steps.cpp`. No tool
  text names a GUI button, "click" or "the user". Response fields named in descriptions must not begin like a tool name
  (`mcp_tool_references.hpp`): `relief_reference`, `section_area_mm2`, not `get_...`, `set_...`, `paint_...`.
- `get_server_info`'s default response stays under 6 KB (no new tool: it should not move). The summary stays
  "Render a plate, object or sliced layer".
- Upstream files change only where a task says so, each with a probe line in CLAUDE.md "Carried upstream fixes" (items
  **CB** in V0, **CC** in V4, **CD** in V5).
- Docs: each task writes its own part of the `### render_plate_view` reference section and its `tool_examples()` entry
  (OrcaMCPServerInfo.cpp ~195). CLAUDE.md's rows, Key Files and Threading Model are V8's, so parallel tasks never edit the
  same doc paragraph.

## V1. Close-ups and the exact camera (5 h, lands 1st)

**Schema** (`views_schema()`): `fit` gains `{box: {min: [x,y,z], max: [x,y,z]}}` and `{point: [x,y,z], radius_mm: r}`
(bed mm, or plate-local with `frame: plate_local`); new view keys `camera_mode` (`fit` default | `exact`),
`projection` (`perspective` default | `orthographic`), `fov_deg` (number 5..120, exact perspective, default 30),
`ortho_height_mm` (number > 0, exact orthographic: the height of the image in mm), `camera` (replay).

**Behaviour**, pure in `OrcaMCPRenderMath.{hpp,cpp}`:

```cpp
// fit: the box a view frames. Box and sphere as given (a sphere's box is centre +- radius); object as today.
BoundingBoxf3 fit_box_of(const FitRequest&, ...);
// camera_mode exact: view = look_at(position, target, stable_camera_up), projection built by hand -- perspective with
// fov_deg vertical (square images, so the same horizontally), near = max(0.5, 0.01 * |target - position|) mm, far =
// the farthest corner of `depth_box` from the eye + 10 mm; orthographic with ortho_height_mm and the same near/far
// along the axis. The camera is never moved (no calc_tight_frustrum_zs_around).
CameraFrame exact_camera_frame(const Vec3d& position, const Vec3d& target, bool perspective, double fov_deg,
                               double ortho_height_mm, int width, int height, const BoundingBoxf3& depth_box);
// mm per pixel on the plane through `target` square to the view (perspective) or everywhere (orthographic).
double mm_per_pixel_at_target(const CameraFrame&, const Vec3d& position, const Vec3d& target);
```

- `camera_mode: fit` (default) keeps today's arithmetic. The custom camera's fit box is the view's `fit` when given (new:
  today a custom camera ignored `fit`), else today's drawn-volumes-plus-20 %. `projection: orthographic` in fit mode
  sets `Camera::EType::Ortho` and the same `fit_zoom_to_box` (its orthographic limit; test it).
- `camera_mode: exact` needs `camera_position` and `target`; a preset or `fit` with it is refused ("exact honours
  camera_position and target; frame a region with fit instead"). `fov_deg` / `ortho_height_mm` without exact refused.
- `camera` (a camera object a render returned, unchanged) replays it: `parse_camera_frame` (OrcaMCPPaintSelect.hpp:144),
  drawn with exactly those matrices (`RenderOptions::camera_frame`); the resolution is its viewport's (a `resolution`
  argument that differs is refused); no other camera key alongside. `camera_position` / `target` in the answer come
  from the replayed camera's own (kept in the object) or are null.
- Every 3D view's answer `camera` gains `camera_mode`, `projection`, `fov_deg` (perspective: from the matrix, as
  `Camera::get_fov`), `mm_per_pixel` (at the target), and `moved: true` with `requested_position` when fit mode backed the
  camera away (it always may, correction 2): an agent reading `camera_position` then knows it is not the eye it gave.
- **Description** (fix the lie about custom cameras): "... A view is a preset or {camera_position, target}. By default
  (camera_mode fit) a custom camera gives only the direction: the picture is zoomed to the view's fit (the plate, an
  object, a box {min, max} or a point with radius_mm) and the eye may be moved back; camera_mode exact honours the eye
  with fov_deg or projection orthographic with ortho_height_mm. Pass a camera a render returned as views[i].camera to draw
  exactly that view again. A close-up is a small fit box, not more pixels: mm_per_pixel says the scale."

Tests (`test_render_math.cpp`, `[RenderMath]`): the target projects to the image centre (exact, both projections); a
point at `fov_deg / 2` off the axis lands on the image edge; `ortho_height_mm` 20 at 512 px gives 0.0390625 mm per pixel;
the near plane is in front of the eye and every `depth_box` corner within [near, far]; `unproject_pixel_to_ray` of the
centre pixel passes through the target and starts at the eye (exact perspective); a 10 mm box framed in fit mode spans
the image within `k_fit_margin` (`screen_bbox_of`); `fit_zoom_to_box` under orthographic equals its orthographic limit.
`test_render_request.cpp`: each refusal above, the replay's resolution rule; `test_mcp_tool_arguments.cpp`: a render
answer's view `camera` sent back as `views[0].camera` passes `tool_arguments_error`.

Reference: the view table rows, "Close-ups" paragraph (fit box vs exact, `mm_per_pixel`, `moved`), one example each.
Golden. Commit `mcp: render_plate_view frames a box or a point, honours an exact camera, and replays a camera`.

## V2. Paint in renders, filament colours (4.5 h, lands 3rd)

**Schema** (top level): `paint` (array of `support`, `seam`, `fuzzy_skin`, `texture`), `texture_layers` (array of
integers 0..7, with `texture`: only these slots; default every slot with a layer), `color_by` (`object` default |

**Pure, new `src/slic3r/GUI/OrcaMCP/OrcaMCPRenderPaint.{hpp,cpp}`:**

```cpp

// support / seam / fuzzy_skin: enforcer TriangleSelectorGUI::enforcers_color, blocker blockers_color (the gizmos'
// own statics, referenced, never copied; fuzzy skin has enforcers only); texture: one colour per slot from a fixed
// 8-colour table that stays apart from the 12-colour object palette and the two gizmo colours (tested).
std::vector<PaintTint> paint_tints(const std::vector<std::string>& channels, const std::vector<int>& texture_slots,
                                   const std::vector<int>& slots_with_layers);
nlohmann::json paint_legend_json(const std::vector<PaintTint>&, const std::vector<PaintCount>&);  // {channel, state, color, label, objects: [{object_id, facets, area_mm2}]}
```

Counts per object and tint from `read_volume_paint(mv, channel)` (OrcaMCPPaintModel.hpp:277). Refusals: an unknown
channel; `texture_layers` without `texture`; a slot no object on the plate has a layer in is listed in

**App side** (an `after_volumes` hook, in `OrcaMCPRenderPaint.cpp`'s app half or a small `OrcaMCPRenderPaintDraw.cpp`):
for each drawn model part and each tint, `annotation_for(mv, channel).get_facets(mv, EnforcerBlockerType(state))`

## V6. Relief colouring (5 h, lands last of B)

**Schema:** `color_by` gains `relief`; `relief_range_mm` (number > 0, optional: the colour ramp's half-range; default the
larger of |min| and |max| measured).

**What it shows, honestly:** each drawn facet coloured by the signed distance of its centroid from a *reference
surface* -- the part as it was before the texture -- on a diverging ramp (raised warm, sunk cool, zero white), 15 bins,
drawn as colour runs. The distance is to the nearest point of the reference (sign from the reference facet's normal),
not along the displacement direction: on steep relief it understates the depth. A legend gives each bin's mm range.

**The reference, by case** (decision 2):

1. **Unbaked, with `texture_preview`:** the captured base mesh of each previewed part (V5) -- exact: what the bake would
   add. Without `texture_preview` an unbaked part has no relief (it is the reference) and is listed with reason
   `"unbaked: add texture_preview"`.
2. **Baked by `bake_texture_displacement`:** the bake already captures each part's pre-bake mesh
   (`TextureDisplacementBakeVolume::base_mesh`, Jobs/TextureDisplacementBakeJob.hpp:31). On a successful apply
   (`finish_bake`, OrcaMCPTextureBakeTools.cpp:322) those meshes move -- no copy -- into a process-wide `BakeReferences`
   store: per baked volume `{volume ObjectID, fingerprint of the baked mesh, base mesh, the volume's matrix at capture}`,
   at most 8 parts or 256 MB, least recently used dropped. A reference is used only while the volume's current mesh has
   that fingerprint (so an undo, a redo onto another mesh, a repair or a re-bake ignores it until a new bake stores one);
   distances are measured in the object's frame through the matrices at capture and now.
3. **Anything else** (a mesh baked in the panel, before this session, or loaded): no reference; listed with
   `"no reference: the surface before the bake is not known"`, drawn in its normal colour. Never guessed.

**Pure, new `src/slic3r/GUI/OrcaMCP/OrcaMCPRelief.{hpp,cpp}`:**

```cpp

                                    const indexed_triangle_set& reference, const Transform3d& reference_to_frame,

nlohmann::json relief_json(...);   // relief: {objects: [{object_id, reference: "unbaked_surface"|"pre_bake_mesh"|null,
                                   //   reason, min_mm, max_mm, mean_abs_mm}], legend: [{from_mm, to_mm, color}]}
```

Distances run in V0's compute step (bounded by the deadline like V5); the bins reuse `group_preview_by_color` to draw.
Combine with `light` (V3) freely. **Next step:** `bake_texture_displacement`'s success answer gets

save_to_file: true}}`; its case in `test_mcp_next_steps.cpp`.

Tests (`test_relief.cpp`, `[Relief][orcamcp]`): a plane raised 0.4 mm gives +0.4 for every facet; a cube against itself

## Risks

1. **GL is untested off this Mac.** No test has a GL context (correction 8); CI compiles the C++ and the shader-file test
   checks text only. A shader that does not compile on a driver (Windows, Linux Mesa, the 110 vs 140 variants) makes
   `GLShadersManager::init` report failure at startup, which breaks the app's renders, not only ours. Mitigation:
   `mcp_render` stays `thumbnail` plus three uniforms in the same GLSL dialect as its neighbours; V9 runs on macOS only;
   ask the Linux agent that tested 2.5.0.8 to run steps 6-10 there before a release.
2. **Memory.** A preview of a fine texture can reach millions of triangles; `GLModel::init_from` duplicates vertices per
   triangle on the GPU, the preview cache holds up to 2 M triangles, and the bake references up to 256 MB. All capped
   and reported, but large on an 8 GB machine.
3. **Time on the -O0 build.** A preview is a bake without simplification: seconds at release speed, minutes at -O0. Past
   the call's wait nothing is drawn for that object and the answer says how to raise the wait; the release build is
   20-70x faster.
4. **An open texture panel** holds strokes the model does not have yet; the preview is drawn from the model and says
   `panel_open`. A render never closes the panel (it would be an undo step).
5. **Relief is distance to the nearest reference point**, not along the displacement: it understates steep relief, and
   it knows the pre-bake surface only for bakes made through MCP in this session (decision 2).
6. **Strict view items** turn today's silently ignored keys into -32602 errors: an agent or script sending extra keys
   breaks once (that is the point; the message lists the keys).
7. **The exact camera's near plane** (0.5 mm or 1 % of the distance) gives coarse depth precision for scenes far behind a
   close eye; z-fighting is possible on coplanar paint tints at long range (polygon offset as the panel's).
8. **Section caps** come from `slice_mesh` of each part; an open mesh gives partial caps (as the 3D view's), and a part
   whose cut is degenerate draws none -- `islands: 0` says so.
9. **Upstream drift.** The texture panel's preview rule (probe CD), the section view's plane (CC) and the shader list
   (CB) are upstream code that changes every sync.
10. **Compare is pixel-level:** antialiasing and label overlays differ by a pixel when anything moves; the threshold
    hides noise, not real small changes.

## Decisions for the user

1. **The texture preview as a `render_plate_view` option** (`texture_preview: true`), reached through next steps from
   the texture tools -- recommended -- or a new tool (e.g. `preview_texture_displacement`, +1 h, counts 111/115 ->
   112/116). The option keeps one place for cameras, close-ups, light, compare and sections.
2. **Relief's reference.** Recommended: the surface the bake displaced, kept in memory for bakes made through MCP in
